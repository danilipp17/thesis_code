\subsection{Runtime Executability}
\label{sec:eval-runtime}
\paragraph{Experiment Setup}

The preceding generation metrics establish structural correctness but not that a generated
system runs and does what its task requires. We therefore execute every generated
artefact and evaluate goal attainment. Each of the 18 generation cells (regenerate
framework~$F$ from the ontology of a system originally written in~$F$) and 36
cross-framework cells (translate from source~$S$ to target~$T$, the six ordered
framework pairs over six task families) is run in an isolated subprocess via
\texttt{runpy}, with the project environment loaded so the agents have model
access, the target directory on the import path and a 90\,s wall-clock budget.
Because LangGraph stores results in graph state rather than standard output, its
entry point is instrumented to print the full final state, so every framework's
product is observable.

Each non-goal cell is then passed through a repair model (\texttt{gpt-5-mini}) once. The prompt provides the full original source of the reference system (code, agent/crew definitions, configuration, tools), the source ontology in Turtle as the semantic specification, the broken generated code with a manifest of its files and the observed runtime failure, under the constraint to keep the target framework, the file layout and the tool-import structure, editing only node/agent bodies, prompt wiring, state access and graph/flow edges. The returned files overwrite a copy of the broken tree and the system is run again and re-judged under the same criterion.
The experiment is single shot (one repair attempt per cell).

\paragraph{Metrics.}

Goal attainment is assessed against each family's intended product: a joke; a code
review naming a concrete finding; a blog article; one or more action items
extracted from a transcript; a travel itinerary; or the arithmetic answer. The
maths family is verified deterministically (the output must contain the
correct result, $(40+12)\times 6 = 312$); the open-ended families are judged by
manual inspection of the produced text against the goal. Importantly, the
artefact must be produced \emph{for the specified task input}: a system that
runs to completion but silently substitutes an input of its own invention (e.g.\
an itinerary for a destination nobody requested) does not reach the goal. Each
run is assigned one of three outcomes:

\begin{itemize}
  \item \textbf{\ding{51}\ Goal reached}: the system runs to completion and
        produces the intended artefact for the specified task input.
  \item \textbf{$\sim$ Partial}: the system runs but does not fully reach the
        goal: it either produces \emph{part} of the goal (e.g.\ an audit without
        the summary, an itinerary without the final-plan field, a transcript
        pipeline that extracts zero tasks) or runs without producing it (empty
        wrapper bodies, or un-wired input --- including runs where the model,
        finding no input, fabricates its own and produces a plausible but
        unrequested artefact).
  \item \textbf{\ding{55}\ Error}: the system does not run to completion (a
        runtime exception, or a timeout).
\end{itemize}

Every non-\ding{51}\ cell is additionally labelled with one \emph{issue category}
naming the dominant cause, defined in Table~\ref{tab:runtime-categories}.

\paragraph{Results}

Before repair, only 3 of 54 generated systems fully reach their goal (3/18
generation, 0/36 cross-framework; Table~\ref{tab:rt-gen-before} and
Table~\ref{tab:rt-cross-before}). Manual inspection is essential here: nine
further systems run to completion and produce a superficially plausible
artefact --- but for an input the model invented itself, because the concrete
task input is never wired in. A bare \texttt{kickoff()} leaves the literal
\texttt{\{topic\}}/\texttt{\{request\}} placeholder in the prompt, or a dummy
seed (\texttt{"sample topic"}) replaces the real value; the model then picks
its own topic, code or destination (the regenerated CrewAI travel planner, for
instance, produced a polished itinerary for Kyoto although the reference
request asks for a 10-day trip to Luxembourg). We score these as input-wiring
partials, not goal attainment. The three genuine successes are all AutoGen
regenerations, which is diagnostic: AutoGen embeds the concrete input in the
\texttt{task=} string of \texttt{run\_stream(...)}, which the ontology captures
as the task description, whereas CrewAI (\texttt{kickoff(inputs=\{...\})}) and
LangGraph (the initial-state seed) bind the input at run time, outside the
ontology, so the deterministic generator cannot restore it. Overall the
non-goal cells are dominated by stub bodies and input wiring: 44 cells run
but produce no, or no usable, output --- together with seven errors (six
crashes and one timeout). A single \texttt{gpt-5-mini} repair pass, given the
original source, the ontology and the broken skeleton and constrained to
produce genuine model-driven output (no hardcoded or framework-bypassing
solutions, verified by re-running each system and requiring its output to vary
across runs), raises goal attainment to 29 of 54 (54\,\%): 14/18 generation
and 15/36 cross-framework (Table~\ref{tab:rt-gen-after} and
Table~\ref{tab:rt-cross-after}). The ``runs-but-no-goal'' category collapses
from 44 cells to one, confirming that the residual gap the deterministic
generator leaves (i.e.\ un-synthesised node/crew bodies and un-interpolated or
un-seeded inputs) is local and fillable once the structure and grounding are
already correct. The cells the repair does not fix surface as genuine
framework-specific errors rather than disguised successes: 24 in total,
dominated by API/idiom mismatches (e.g.\ calling a LangChain
\texttt{StructuredTool} or \texttt{ChatOpenAI} object directly, or assigning to
\texttt{StateGraph.state}) and agent-schema validation failures (i.e.\ faults
that require deeper, framework-specific synthesis than a single pass provides).
